The goal is to systematically test the real user interface through actual UI interactions, similar in discipline to unit testing, but focused on user-facing behavior rather than isolated functions. These tests should exercise the app the way a user would: opening pages, navigating between views, clicking buttons, scrolling panels, triggering drawers/modals, capturing screenshots, interacting with forms, resizing windows, and verifying that the UI remains stable.

The test matrix must cover all product surfaces:

1. Desktop app
2. Browser app
3. Demo browser experience
4. Mobile / responsive layout

The desktop app should be treated as the primary target and receive the deepest coverage. The browser app, demo browser, and mobile/responsive versions should still be tested, but their coverage should still verify parity, layout integrity, navigation, and major user flows.

The test suite should not only check that pages load. It should actively interact with the UI and verify that core flows work without visual collapse, broken navigation, unresponsive controls, layout overflow, inconsistent state handling, or runtime errors.

Because Kaur Khor’s UI states are highly dependent on underlying data, the test suite must explicitly check for data-state-specific regressions. The same UI component may behave differently depending on whether the workspace is empty, freshly initialized, populated with generated data, or evolved through organic user updates. The test matrix must therefore separate tests by data state, not just by page or product surface.

Create three major test matrices:

1. Fresh-state matrix

This matrix covers a newly initialized workspace with little or no user data.

Use this to verify:

- First-run experience
- Empty states
- New workspace setup
- Default navigation
- Pages with no SKUs, services, observations, orders, tickets, or generated history
- Empty tables, empty charts, and empty drawers
- Disabled actions and unavailable controls
- Guidance copy, onboarding hints, and safe defaults
- Whether the app avoids crashes when expected data does not exist yet

The fresh-state matrix should answer:

- Does every page render correctly with no data?
- Are empty states useful and visually stable?
- Are buttons, forms, and navigation still usable?
- Are unavailable actions disabled or explained correctly?
- Does the app avoid showing misleading metrics, NaN values, broken charts, or placeholder leaks?

2. Autogenerated-state matrix

This matrix covers states created from generated/demo/test data.

Use this to verify:

- Demo data behavior
- Generated SKUs and services
- Generated observations
- Generated demand, sales, supplier orders, customer orders, stock counts, receipts, and price/cost changes
- Generated charts, tables, projections, and inventory health metrics
- Demo browser mode
- Screenshot/capture stability across representative populated states

The autogenerated-state matrix should answer:

- Does the app render realistic populated workspaces correctly?
- Do tables, charts, cards, and detail pages handle generated data consistently?
- Do filters, sorting, search, collapsible sections, and drawers work with populated data?
- Are demo-data banners, reset controls, import/export actions, and local-first browser behavior working?
- Do generated edge cases reveal layout overflow, bad formatting, broken calculations, or chart instability?

3. Dependent-state matrix

This is the most important matrix.

This matrix covers organic user updates that extend from a fresh workspace into increasingly complex real-world states. It should test the consistency of the underlying data handling as the user gradually builds the workspace through normal use.

Use this to verify workflows where app state depends on previous user actions, such as:

- Creating a SKU or service
- Adding the first stock count
- Adding follow-up observations
- Updating price or cost
- Recording customer orders
- Recording immediate sales
- Recording pending customer orders
- Completing customer orders
- Recording supplier orders
- Updating supplier orders
- Recording supplier receipts
- Changing expected arrival dates
- Editing or correcting previous records
- Moving from sparse observations into richer time series
- Checking whether changes propagate correctly across Overview, Catalog, SKU detail, Service detail, Inventory/Insights, Performance, Analysis, and Logs

The dependent-state matrix should answer:

- After a user records an update, does the new state appear consistently everywhere?
- Do derived values update correctly across all affected pages?
- Do charts, tables, alerts, tasks, tickets, and summaries agree with the same underlying data?
- Does the app preserve consistency after sequential updates?
- Do edits, corrections, and follow-up updates avoid stale UI state?
- Does the app avoid contradictory values between Overview, detail pages, Logs, and analysis surfaces?
- Does local persistence work after reload, close/reopen, route changes, and product transitions?
- Does the UI remain stable when data evolves from sparse to richer states?

Required coverage areas across all matrices:

- App launch and initial render
- Main navigation between all major sections
- Desktop-specific workflows and layouts
- Browser app workflows and local-first behavior
- Demo browser mode, including demo-data banners and reset/import/export controls where available
- Mobile and responsive breakpoints
- Button interactions
- Form inputs and dropdowns
- Modal, drawer, popover, and panel behavior
- Scroll behavior in long pages, nested panels, charts, and tables
- Screenshot/capture checks for key pages
- Empty states, loading states, and error states
- Window resizing and layout stability
- Route changes and back/forward navigation
- Data persistence after reload or app restart
- Data consistency across pages after user updates
- Known fragile UI areas, especially charts, drawers, configurable tables, inventory health views, logs, tickets, and dynamic data pages

Each test case should clearly define:

- Product target: desktop app, browser app, demo browser, or mobile
- Data-state matrix: fresh state, autogenerated state, or dependent state
- Page or feature area
- Initial data setup
- User interaction being tested
- Expected UI result
- Expected data/state result
- Cross-page consistency checks
- Priority level
- Test type: smoke, regression, visual, interaction, stateful, or end-to-end
- Screenshots or captures required
- Notes for edge cases

Recommended implementation structure:

- Prioritize the desktop app first.
- Prioritize the dependent-state matrix above all other matrices.
- Add fresh-state tests to protect first-run and empty-workspace behavior.
- Add autogenerated-state tests to provide broad populated-state coverage.
- Add browser app, demo browser, and mobile/responsive coverage after the desktop baseline is stable.
- Avoid duplicating identical tests unnecessarily; use shared test helpers where possible.
- Use seeded/generated data where determinism is important.
- Use organic user-driven updates where state transition correctness is important.
- Make the matrix easy to expand as new pages, workflows, and state types are added.

The final implementation should produce an automated UI regression test suite that can be run consistently during development to catch broken navigation, broken layouts, interaction bugs, visual regressions, state propagation bugs, data-specific regressions, and product-specific UI failures before release.
