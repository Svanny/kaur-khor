# Redis Cache and Coordination Policy

## Purpose
Redis is a performance optimization and lightweight coordination layer. It is never required for correctness.

## Correctness Boundary
- Postgres is the source of truth.
- Write idempotency correctness is enforced in Postgres (`app.idempotency_request`) using unique constraints and persisted request outcome.
- Redis idempotency data is cache acceleration only.

## Fail-Open Rules
- If Redis is unavailable, API requests continue via source-of-truth path.
- Redis operations must fail fast with explicit connect/command timeouts.
- Circuit breaker suppresses repeated Redis attempts during outages.
- Warning logs are rate limited during incidents.

## Required Configuration
- `REDIS_URL`
- `CACHE_ENABLED`
- `CACHE_SCHEMA_VERSION`
- `CACHE_DEFAULT_TTL_SECONDS`
- `CACHE_TTL_JITTER_SECONDS`
- `REDIS_CONNECT_TIMEOUT_MS`
- `REDIS_COMMAND_TIMEOUT_MS`
- `REDIS_CIRCUIT_ERROR_THRESHOLD`
- `REDIS_CIRCUIT_WINDOW_SECONDS`
- `REDIS_CIRCUIT_COOLDOWN_SECONDS`
- `REDIS_LOG_RATE_LIMIT_SECONDS`

`CACHE_SCHEMA_VERSION` is required and must be set explicitly per environment.

## Key Naming Contract
All keys are generated by central key builder and include:
`{system}:{env}:{service}:{cache_schema_version}:{domain}:{...}`

No ad hoc Redis key strings are allowed.

## Lock Contract
Locks are best-effort coordination only.
- Acquire: `SET key token NX EX ttl`
- Release: compare-and-delete with token match (Lua script)

Never use Redis locks as correctness gate for durable state changes.

## Stampede Controls
- Default TTL jitter is required for cache writes.
- Use in-process single-flight on hot key paths to reduce thundering herd.
- Endpoint-specific TTL overrides are allowed.
